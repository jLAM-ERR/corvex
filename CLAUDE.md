# CLAUDE.md

## Overview

Rust CLI tool (`corvex`) that manages the Xray VPN daemon and system proxy settings on macOS, Linux, and Windows. Supports AmneziaWG as an alternative tunnel engine.

## Build & test

The gate CI enforces, verbatim from CONTRIBUTING.md — note the `-A dead_code`,
without which clippy fails on the intentionally-unused Windows platform module:

```bash
cargo test                                # Unit tests
cargo clippy -- -D warnings -A dead_code  # Lint (warnings are errors)
cargo fmt --check                         # Formatting
shellcheck install.sh                     # When touching install.sh
```

Tests never call `tempfile::tempdir()` directly — `config::test_tempdir()` is
the one entry point, because `tempdir` creates the directory with `0777 &
!umask` and `ensure_trusted_ancestry` judges exactly those mode bits. A shell
at `umask 002` therefore hands the suite a group-writable directory, which
macOS refuses by design (the group is `staff`, which holds every local
account), and fifty-odd tests fail on a developer's machine while passing in
CI, whose umask happens to be 022. `test_tempdir` sets 0700 explicitly;
subdirectories a test creates underneath it need `create_dir_restricted` for
the same reason, not `create_dir_all`.

The toolchain is pinned in `rust-toolchain.toml` (1.97.1, `minimal` profile,
rustfmt + clippy, plus the three cross targets the release workflow builds).
Alpine's packaged rustfmt disagreed with the Mac's, so `cargo fmt --check`
passed or failed depending on where it ran. `ralphex-rust.Dockerfile` is the
matching container — the stock ralphex image ships Go, not Rust:
`docker build -t ralphex-rust:latest - < ralphex-rust.Dockerfile` (note the `-`:
no build context, the repo carries a multi-GB `target/`). **Bumping the
toolchain means changing both `channel` and `ARG RUST_VERSION`**; the image also
installs `procps`, because busybox `ps` rejects the flags `xray.rs` uses and four
process-tracking tests fail without it.

## Usage

```bash
cargo run -- start                              # Load corvex.json, resolve server, start
cargo run -- stop                               # Stop xray first; system proxy is disabled (+ AWG stopped) only if the stop succeeded
cargo run -- restart                            # Full stop + start: restarts xray, re-applies system proxy
cargo run -- reload                             # Validate config, send SIGHUP
cargo run -- status                             # Show engine type, xray process, ports, proxy settings
cargo run -- dns                                # Diagnose system resolvers: route -> interface -> next-hop on-link check -> UDP:53 probe (macOS full, Linux narrower, Windows unimplemented)
cargo run -- logs                               # Show last 20 lines of the *xray* log (not corvex.log)
cargo run -- logs -f                            # Follow the xray log (tail -f)
cargo run -- --settings /path/to/corvex.json start  # Use custom settings file
CORVEX_DEBUG=1 cargo run -- start               # Raise the level to debug (default is info)
```

### corvex.json

All configuration is in a single JSONC file at `$XDG_CONFIG_HOME/corvex/corvex.json`:

```jsonc
{
  "uri": "vless://uuid@host:443?...",           // Proxy URI (vless/vmess/trojan/ss/vpn)
  "subs-url": ["https://sub1.com/link"],        // Subscription URLs for auto-discovery (legacy alias: file-url)
  "subs-user-agent": "Happ/3.13.0",             // UA for subs-url downloads; default "v2rayNG/1.10.2"
  "subs-headers": { "X-Hwid": "abc" },          // Extra headers for subs-url downloads; a "User-Agent" key here wins over subs-user-agent
  "proxy": { "port": 21080 },                   // REQUIRED: static proxy port
  "corporate-dns": { "corp.com": "10.0.0.1" },  // Domain -> nameserver mappings
  "routes": {
    "proxy-traffic": ["domain:ext.com"],         // Force through proxy
    "corporate-traffic": ["domain:corp.com"],    // Bypass proxy (direct)
    "merge-subs": false                          // Merge the subscription's direct rules into routing; transitional (default off, security-sensitive; see README) — expected to become the default and be removed in a future release
  },
  "log": {
    "xray": { "loglevel": "warning" },            // access/error default to $XDG_STATE_HOME/xray/{access,error}.log (%LOCALAPPDATA%\xray\ on Windows); override e.g. "/var/log/xray/access.log"
    "corvex": { "debug": false }
  }
}
```

## Non-obvious module behavior

- `traffic.rs` — always emits a leading rule that routes `127.0.0.0/8`, `::1/128`, and `geoip:private` to the `direct` outbound. This rule is unconditional and cannot be disabled via corvex.json — tunneling loopback or RFC1918 through a public VPN exit never works.
- `jsonsubs.rs` — parses JSON-array subscriptions (a JSON array of complete xray configs, one per server; the format panels serve to clients such as Happ) and harvests their direct rules for `routes.merge-subs`.
- `xray.rs` — presence check only, no auto-install: a missing binary is a hard error pointing to install.sh. Sets `XRAY_LOCATION_ASSET` to the install.sh-managed geo data dir only when the env var is unset and both geoip.dat and geosite.dat exist there. Read-only process listing (`ps -eww -o pid=,user=,args=`) classifies every xray process by the `-c` config path it was launched with — managed (matches corvex's own config.json), orphan (managed but untracked), or other xray (different config) — and corvex never signals a process it does not track. Known blind spot: sudo resets HOME, so a root-launched corvex may use a different config path and its own process then classifies as "other xray" instead of a detected orphan. `xray.pid` is written the same way the xray config is: `config::open_write_restricted` (`O_NOFOLLOW` + `O_NONBLOCK` + `accept_restricted_file` + 0600, and no `OpenOptions::truncate`) at *both* the pre-spawn writability preflight and the post-spawn write, because a plain `fs::write` there follows a symlink and truncates its target — an arbitrary-file clobber in the same world-writable `/tmp` fallback, and the PID path is not configurable, so nothing but corvex has a reason to create it. A symlink or FIFO found at that path is refused by name (`unsupported_pid_file_shape`) rather than followed *or* unlinked: corvex neither writes through someone else's plant nor turns it into a way to get files deleted. The xray *process* log is opened through `config::open_xray_log`, which picks the trust level from who chose the path — the strict `open_append_restricted` for every path corvex picked itself, and `open_append_nonblocking` for one the user named in `log.xray.*`, where a symlink is redirection they set up and `/dev/null` or a FIFO with a reader are legitimate. "Corvex picked it" is `config::is_corvex_chosen_xray_log`, and it covers **three** paths, not one: `$XDG_STATE_HOME/xray/xray.log` plus the default `access.log` and `error.log` that `protocol::XrayLogConfig::default` writes into xray's generated config. Only `xray.log` used to be listed, which left corvex following a symlink planted at either of the other two — creating its target during the preflight, in the same plantable directory — so those two defaults are now spelled once, in `config::default_xray_access_log`/`default_xray_error_log`, and a test pins `XrayLogConfig::default` to what the predicate recognises. The lenient open is still `O_NONBLOCK` (cleared again before the descriptor becomes xray's stdout/stderr), so a readerless FIFO anywhere in the log config fails the start instead of wedging it. `main.rs::preflight_log_paths` probes through the same function, so the preflight tests the open the spawn will actually make. The probe is a snapshot, though, and for `access.log`/`error.log` it is not even the open that matters — xray reopens those two by *name*, out of the generated config, after the preflight has closed (and possibly removed) what it created. So `config::ensure_trusted_ancestry` runs before the strict open: every directory from the log's own up to `/` must be owned by the effective uid or root and grant no write to group or other, sticky directories (`/tmp`, 1777) excepted because sticky is precisely what stops one user renaming another's entry. Group write has a second exception, and it is not a softening: it is refused unless the group is this user's own private group, which `config::group_write_is_private` establishes from three things — `gid == euid` (the user-private-group convention), `getgrgid` listing no supplementary members, and, on Linux, no POSIX ACL stored on the directory. Without it corvex refused the default shape of a Debian or Ubuntu home: those ship `USERGROUPS_ENAB yes` with `pam_umask`, which lowers a normal user's umask to 002 *because* their primary group holds them alone, so `~/.config`, `~/.local` and `~/.local/state` land at 0775 owned by `alice:alice` and `start` aborted on a stock install. `gid == euid` is also what keeps macOS strict — every local account there is in `staff` (gid 20) while uids start at 501, so no group-writable directory on macOS is ever called private. In a chain like that nothing can be planted between the probe and the spawn, which is what turns a point-in-time check into a lasting one. The walk resolves the chain itself, component by component, rather than starting from `canonicalize`: canonicalizing reports the directories the name resolves to *now*, and xray reopens the name, so a walk over the canonical chain never judges the directory holding a symlink — an attacker-owned `/tmp/.local` could point at a trusted tree while the check ran and anywhere else by the time xray opened the log, sticky `/tmp` notwithstanding, since sticky stops everyone except the entry's owner. Each symlink met on the way is judged by `untrusted_link_rejection` (owner only: a symlink's mode bits mean nothing) and then its target is walked in turn, bounded by `MAX_ANCESTRY_SYMLINKS` because the walk, not the kernel, is following the links. It is asked of **every** corvex-chosen restricted path, not only of the two logs xray reopens: it is inside `open_write_restricted`, inside `open_append_restricted`, and at the top of `rotate_if_oversized`, so `config.json`, `xray.pid`, `corvex.log` and `xray.log` are all covered and no future caller can forget it. Two distinct gaps make that necessary. The name-leaves-the-process one is the same as the logs': `config.json` carries the VLESS UUID or Trojan password and its *path* is what goes to `xray run -c`, so anyone who can swap that entry between the write and the spawn picks xray's inbounds and outbounds. The second applies even where corvex never lets go of the descriptor, and is why `xray.log`'s old exemption ("corvex opens it here and hands over the vetted descriptor") was wrong: `O_NOFOLLOW` governs the *final* component only, the kernel resolves every parent as usual, so an ancestor another account can repoint decides *which* file the vetted descriptor is on — `/tmp/.config/xray` pointed at a directory holding a readable `config.json` of corvex's own uid passes the owner, regular-file and link-count checks, is tightened to 0600, truncated and filled with credentials that a reader who opened it beforehand keeps receiving. `create_dir_restricted` is no help there: it leaves an existing ancestor exactly as found, deliberately, and a symlink to a real directory is what "existing" looks like. `rotate_if_oversized` needs it in its own right — it is the one step that acts on the name (`remove_file`, `rename`) rather than through a descriptor, and `prepare_log_file_at` runs it *before* the open. A chain that fails the check is a hard error naming the directory and the `chmod`. Naming both logs in `log.xray.*` is still the way out when it is the *log* directories it objects to (a group-writable `/var/log/xray`), but it no longer rescues a home directory owned by another uid, since `config.json`, `xray.pid`, `corvex.log` and `xray.log` have no configurable paths; `XDG_CONFIG_HOME`/`XDG_STATE_HOME` are the answer there, and `config::with_log_escape_hatch` says both. The pure `untrusted_ancestor_rejection` holds the decisions, since a foreign-owned directory is not something the suite can stage. On macOS the mode bits are not the whole story, so each directory's extended ACL is read too (`config::extended_acl_text`, `acl_get_link_np` so a link that appeared since the `lstat` is not followed) and judged by the pure `untrusted_acl_rejection`: an ACL is consulted *ahead* of the mode, so `chmod +a "bob allow add_file,delete_child"` leaves a directory `stat` still calls 0700 that bob can swap entries in for as long as it exists. Only `allow` entries count (`everyone deny delete` sits on half a stock home), a `user` entry naming this uid or root is the same trust boundary restated, and everything else granting one of `ACL_MUTATION_RIGHTS` is refused with the `chmod -N` that clears it — `group` included, because a group holds other accounts exactly like the group write bit the mode check already refuses. The line is read by position from the left (`<user|group>:<uuid>:<name>:<id>:<verdict>[:<rights>]`), the way `acl_from_text` reads it back, because counting from the right slips a field on the two shapes Darwin also renders: an ACE granting nothing has no rights field *and* no colon in front of one, and the verdict field carries the entry's inheritance flags appended to it — `allow,inherited` is every ACE of a directory that inherited its ACL, and reading the verdict as the whole field refused all of them as unreadable, failing `start` on an ordinary tree. The flags themselves are still not *read*: an ACE that only propagates describes what the directories corvex creates underneath it will grant. Linux needs no equivalent reader for the general case: there the group mode bits *are* the POSIX ACL mask, so `setfacl -m u:bob:rwx` on a 0700 directory shows up as 0770. Surfacing in the mode is only half an answer now that a private group makes that bit acceptable — bob's grant would ride in under it — so `config::has_posix_acl` asks `lgetxattr` for `system.posix_acl_access` and any ACL at all disqualifies the private-group exception. Presence is enough; the blob is never parsed, and the question is only asked when the group write bit is actually set, so the ordinary directory costs neither the `getgrgid` nor the `lgetxattr`.
- `engine/awg.rs` — presence check only, no auto-install: a missing awg-quick is a hard error pointing to a manual amneziawg-tools install. The .conf goes through `ensure_conf_trusted` at all three handoffs (`write_conf`, `start_tunnel`, `stop_tunnel`), which is `config::ensure_trusted_ancestry` under a message about root: `write_restricted` vets the descriptor it writes the private key through, but the *name* is what leaves the process — `sudo awg-quick` reads it as root and runs its `PreUp`/`PostUp`/`PreDown`/`PostDown` lines as root shell commands, so anyone who can replace an entry on that chain between the write and the `sudo` has a root shell. The `$XDG_CONFIG_HOME`-unset fallback puts the file under `/tmp`, which is where it matters. `stop` checks too, because it runs against a file an earlier `start` wrote into a directory that may have been widened since.
- `subscription.rs` — every download is built from `subscription_agent_config()`, which sets `.proxy(None)` **by design** (the regression test re-runs the test binary as a child process with `ALL_PROXY` set in the child's environment, because the assertion is vacuous on a machine with no proxy variable set and `set_var` would race every sibling test reading the environment). ureq 3's `Config::default` picks a proxy up from `ALL_PROXY`/`HTTPS_PROXY`/`HTTP_PROXY` (and lowercase), and a shell exporting `HTTP_PROXY=http://localhost:<proxy.port>` points that at corvex's own listener — which `start` has not launched yet, so the fetch deadlocks against the tunnel it exists to bring up (surfaces as `timeout: global` then `no supported proxy servers found in subscriptions`). Do not "restore" environment proxy support here; an opt-in `subs-proxy` key would be the way, and no one has asked for it. Relatedly, no subscription URL is ever rendered whole: `redact_url` keeps scheme+host (+non-default port) and replaces userinfo/path/query/fragment with `<redacted>`, because panels put the access token in the path. It is applied on every log, progress and error path (`subscription_failure_message`, `subscription_progress_message`, `subscription_download_line`), and an unparseable URL renders as the marker alone rather than being echoed. `download_subscription` additionally refuses anything that is not `http`/`https` with a host *before* handing the string to ureq, whose `BadUri` renders the whole URI — a scheme `url::Url` accepts but ureq cannot fetch (`mailto:<token>@host`) would otherwise carry the token into `{err:#}` past every `redact_url`. Redaction covers only the URL *corvex* chose, though, so the transport error is described before it becomes an `anyhow::Error`: `describe_fetch_error`/`describe_io_error` map a `ureq::Error` to text corvex composed, because `Protocol` carries ureq-proto's `BadLocationHeader(String)` — the raw `Location` of a redirect ureq could not parse — and `BadUri(String)` renders a whole redirect-derived URI, so a panel reflecting the request path back in a `Location: ../../../<token>` writes the token to `corvex.log` at the default level (and a hostile one writes arbitrary bytes, terminal escapes included). The arms keep every diagnosis worth reading (`timeout: global`, `host not found`, `http status 403`, the OS text of an `io` error) and the `#[non_exhaustive]` catch-all makes a future ureq variant safe by default; `describe_io_error` unwraps a `ureq::Error` boxed inside an `io::Error`, which is how a body-read fault arrives. Sentinel-token tests guard both the success and failure paths — a new line that interpolates a raw URL, or a `?` that lets a ureq error reach `{err:#}` undescribed, will break them.
- `main.rs` logging — `TeeWriter` fans `env_logger` output to stderr *and* `config.corvex_log`, opened append-only at 0600 via `config::open_append_restricted` (which also tightens the mode of a file already at that path left looser by something else, but refuses a symlink outright: the open carries `O_NOFOLLOW`, and the mode is tightened with `fchmod` through that descriptor rather than through the path — under the `/tmp` `HOME` fallback the log sits in a world-writable directory, where a planted link would otherwise be an arbitrary-file-append, and a second path resolution for `chmod` would be a TOCTOU on top of it. `O_NOFOLLOW` rules out only the symlink, so the open also carries `O_NONBLOCK` and hands the descriptor to `accept_restricted_file`, which refuses three more shapes the same world-writable directory admits. Not a regular file: `mkfifo` needs no privilege, and a planted FIFO with no reader would block the open forever — a whole-CLI denial of service that lands before the logger or the command exists — while one the attacker holds open for reading would take every `info!` line. Not owned by the effective uid: `.mode(0o600)` applies only to a file the open *created*, so an `install -m 666 /dev/null` planted at the path is the cheapest attack of all, and it has to be refused rather than `fchmod`ed — that call *succeeds* under root and leaves the attacker owning a file they chmod straight back. `nlink != 1`: `O_NOFOLLOW` says nothing about hard links, and a link to a file corvex's own uid owns passes the ownership test on the victim's ownership. The decisions live in the pure `restricted_file_rejection`, because becoming a second uid is not something the suite can stage. `write_restricted` carries all of it and cannot be reused here regardless, it truncates — and it truncates with `set_len` on the vetted descriptor rather than `OpenOptions::truncate`, which fires inside `open`, before any check has run. The config dir falls back to `/tmp` the same way, so it is plantable too; `config::create_dir_restricted` is the defence in depth behind all of this — every corvex-created directory component lands at 0700, and an existing directory is left exactly as found, deliberately. One hole the mode bits do not close at all: macOS ACLs are inherited from the directory, evaluated ahead of the mode, and invisible to both `stat` and `fchmod`, so an attacker who pre-creates the fallback hierarchy with a `file_inherit` ACE gets a readable copy of every file corvex later creates there while owning none of them — `strip_inherited_acl` removes the extended ACL through the descriptor on every restricted open, and is a no-op off macOS because Linux's POSIX ACL mask is recomputed from the group bits of a 0600 mode. Stripping is not the whole answer for a *credential*, though: the file carries the inherited ACE for the two syscalls between `open` and the strip, and a descriptor somebody opened in that window keeps reading the inode afterwards. So `strip_inherited_acl` reports whether it actually removed anything, and `write_restricted` treats "yes" as "this inode may already be shared" and re-does the write through `write_via_private_dir` — `mkdir` a fresh 0700 directory beside the target, strip *its* inherited ACL through a descriptor, create the file inside it (a file created under a directory with no extended ACL inherits nothing, so there is no window at all), then `rename` it into place, which applies no inheritance. `open_append_restricted` does the same for a log — a stripped ACE does nothing about a descriptor obtained in that window, and its holder would go on reading every line appended to `corvex.log` and `xray.log` — but through `append_via_private_dir`, which differs in one respect: a log has a past worth keeping, so the bytes already in it are copied into the replacement *through the descriptor just vetted* (which is why `open_append_vetted` opens read-write) rather than through a second resolution of the name, and only then is the replacement renamed into place. `create_in_private_dir` is the shared middle of both. `xray.pid` keeps the plain open because a PID is not a secret. The ACL is *read* with `acl_get_fd_np`, and `EINVAL` from it is not read as "nothing to strip" — Darwin raises it in libSystem for one reason, an `acl_type` other than the `ACL_TYPE_EXTENDED` constant, so treating it as benign would mean writing a credential through a descriptor whose ACL is still on it; the filesystem-does-not-do-ACLs case is `ENOTSUP`/`EOPNOTSUPP`, which are distinct errnos on Darwin and both accepted. The strip itself writes an empty `acl_init(0)` through `acl_set_fd_np`, and **not** `acl_delete_fd_np`, which is the call it reads like it should be: that one fails with `ENOTSUP` on current macOS for every descriptor and every file — libSystem implements it as `fremovexattr` of the ACL pseudo-attribute, which the kernel refuses on APFS, and the path-based `acl_delete_link_np` behaves identically — and it fails *after* `acl_get_fd_np` has reported an ACL present, so the error arm was the only reachable outcome on exactly the files the function exists for: a directory handing an ACE down turned every credential write into a hard `PermissionDenied` instead of stripping it. An empty ACL leaves the end state Darwin's own `chmod -N` does). Rotation to `corvex.log.1` past `LOG_MAX_BYTES` (5 MB) happens before the open. The default level is `info`, not `warn`, because the file is now the record of what a `start` did; `phase_line` is the single format for every start-path progress line. A file that cannot be opened or written degrades to stderr-only for the rest of the process, reported once — logging never aborts a command. `init_logger` must run after `Config` is resolved, since it creates the log's parent directory itself. `main` reports the terminal error through `report_terminal_error`, which takes the level check as a parameter so "never both" is testable: `error!` so the failure that ended a run reaches the file too, falling back to stderr only when the level filter would drop it (`RUST_LOG=off`) — never both, and never a `colored` string through the logger, which would put ESC bytes in the file that `WriteStyle::Never` only suppresses for env_logger's own rendering.
- `dns.rs` — `parse_scutil_dns` returns `Vec<ResolverEntry>`: **all** nameservers of each resolver (so a failover pair survives) and resolvers with no `domain` line (the machine's primary resolver typically has none). It stops at the `DNS configuration (for scoped queries)` header, because scutil prints every resolver a second time there, renumbered from `#1` — parsing both would list and probe each nameserver twice. `corporate_mappings_first` is the deliberately lossy projection feeding the xray path — it drops domain-less resolvers, skips zone-scoped IPv6 literals (xray reads a non-literal `dns.servers[].address` as a *domain*), and keeps only the first usable nameserver, preserving `discover_corporate_dns`'s `BTreeMap<String, String>` signature. Acceptable only because the xray DNS block is inert; widening it is tracked in `docs/plans/20260824-dns-parser-fixes-and-diagnostic-command.md`. `platform/linux.rs::resolver_entries` is the same kind of projection in reverse, and is lossier still (one nameserver per domain, no interface, no global resolver) because the `resolvectl` parser has the identical unfixed bug.
- `platform/mod.rs` — `NextHop::from_route` is the last step of every `Platform::next_hop_status`: run `route_is_on_link` and carry the route's gateway and interface across. Shared because the tail was byte-identical in the macOS and Linux impls, and because it is the only part of that path a test can reach without running a command.
- `netdiag.rs` — the next-hop verdict is *computed*, not ARP-probed: `next_hop_on_link` compares the gateway against the address and netmask of the interface the route named. ARP state is racy and needs privileges to read meaningfully, whereas subnet arithmetic over three values is exact, pure and unit-testable — and an off-subnet gateway is exactly the incident this diagnostic was built for (a stale VPN host route pointing at a gateway not on-link, so every query died with `sendto: Network is unreachable` while each layer looked healthy alone). IPv4 only, and it fails *open* in every case where the arithmetic cannot decide — no gateway, no readable interface address, or an interface whose addresses are *all* host masks — the point-to-point `/32` of a `utun`/`wg`, whose peer gateway is legitimately off-subnet. That exemption belongs to the interface, not to one address: a `/32` beside a real subnet is a service alias (VIP, anycast, bridge helper) and is skipped, because counting it as a match let one alias report every gateway on-link. The parsers return **every** `inet` line, and a gateway matching any one alias is on-link; both parsers reading only the first address was a false-positive source. `cmd_dns` diagnoses each address once and reuses the rendered line, because macOS emits one resolver block per split-DNS search domain and a dozen of them routinely share one failover pair — without the memo a silent-but-on-link pair costs the 2s probe timeout per block. It skips a nameserver that is not an IPv4 literal (`is_diagnosable_nameserver`) and prints `not diagnosed` — `route get` and the probe socket both reject a zone id like `fe80::1%en0`, so walking one rendered a healthy resolver as a red failure. The UDP/53 probe hand-rolls the query (12-byte header + QNAME + QTYPE/QCLASS) rather than adding a DNS crate, and is split into pure `build_dns_query`/`parse_dns_response` (tested) plus the socket layer, which is `probe_udp53_at(SocketAddr, …)` with `probe_udp53` pinning port 53 on top — the split exists so the tests can drive the real probe against a loopback responder instead of a resolver, so no test ever makes a real DNS query. corvex only ever *reads* the route table; it does not and will not change routes.
- `platform/macos.rs` — proxy changes are applied as a batch: `enable_proxy`/`disable_proxy` build their command lists with the pure `enable_proxy_commands`/`disable_proxy_commands`, then hand them to `run_networksetup_all`, which runs each unelevated and — on the first "requires admin privileges" — re-runs the *whole* batch inside one `osascript ... with administrator privileges`, so macOS asks for the password once instead of once per command. Both the unelevated (`classify_networksetup_output`) and elevated (`classify_elevated_output`) paths treat `** Error` on either output stream as a failure even when the exit code is 0, because networksetup reports errors inconsistently.

**Design principles:**
- All parsing functions take `&str` — unit testable without system calls
- PID-based process tracking with stale PID cleanup
- Config validation before reload (parse JSON before sending SIGHUP)
- Static proxy port from `proxy.port` in corvex.json (required)
- EngineMode enum with match dispatch (Xray vs AWG)
- Platform abstraction via cfg-gated concrete types (no dynamic dispatch)
- Command functions take `&impl Platform` — unit-tested against the `RecordingPlatform` mock in `src/main.rs` tests (records calls, configurable failures, no real system calls)
- Loopback and RFC1918 are short-circuited to `direct` at the top of `routing.rules` (see `traffic.rs::build_routing_rules`)

## Key paths

### Unix (XDG Base Directory)
- corvex.json: `$XDG_CONFIG_HOME/corvex/corvex.json` (default `~/.config/corvex/corvex.json`), overridable via `--settings`
- Xray config: `$XDG_CONFIG_HOME/xray/config.json`
- PID file: `$XDG_CONFIG_HOME/xray/xray.pid`
- Corvex log: `$XDG_STATE_HOME/corvex/corvex.log` — append-only, mode 0600, rotated to `corvex.log.1` past 5 MB
- Xray logs: `$XDG_STATE_HOME/xray/{access,error}.log` by default; configurable via corvex.json `log.xray.*`

### Windows
- `%APPDATA%`/`%LOCALAPPDATA%` fall back through `config::windows_per_user_dir`: the variable, then the same directory rebuilt from `%USERPROFILE%`, then `std::env::temp_dir()`. It used to fall back to `C:\Users\Public\AppData\{Roaming,Local}`, which was this platform's whole exposure — Public grants every account on the machine full access *by inheritance*, so the generated xray config (VLESS UUID, Trojan password) was readable by everyone the moment it existed, and the directories were plantable with a junction or with a pre-created file whose DACL the attacker chose. No check on a *handle* fixes that, because the permissions come from the parent, so the fix is not to write there; `%USERPROFILE%` is set wherever `%APPDATA%` is and in most places it is not, and it being an environment variable is not a hole: it belongs to the user running corvex, exactly as `$HOME` and `$XDG_STATE_HOME` do on unix. `std::env::temp_dir` is the last resort and is the one location here that is *not* per-user by construction — `GetTempPath` reads `%TMP%` and `%TEMP%` first, a service started from the system environment block gets `C:\Windows\Temp`, which every account may create entries in, and Rust's own docs warn the value may be shared. So corvex writes none of its files there: `config::shared_fallback_rejection` (asked by `open_write_restricted`, `open_append_restricted` and `create_dir_restricted`) turns that fallback into a hard error naming the variables to set, rather than inheriting a DACL it cannot vouch for. There is no handle check that would substitute — on Windows the permissions come from the parent.
- The restricted opens (`open_write_restricted`, `open_append_restricted`) carry `FILE_FLAG_OPEN_REPARSE_POINT` and refuse a handle whose attributes come back with `FILE_ATTRIBUTE_REPARSE_POINT`: a *directory junction* needs no privilege at all to create (unlike a file symlink), and following one at `xray.pid` or `corvex.log` is an arbitrary-file clobber with corvex's privileges. The flag governs the final path component only — a junction on a parent directory is still traversed. There is no Windows twin of `ensure_trusted_ancestry` (no uids, no mode bits); what stands in for it is that the hierarchy is per-user by the resolution above and `create_dir_restricted` creates it before anything is written into it.
- corvex.json: `%APPDATA%\corvex\corvex.json` (`%APPDATA%` unset falls back to `%USERPROFILE%\AppData\Roaming`; with that unset too, corvex refuses to write rather than use `%TEMP%`, which may be shared)
- Xray config: `%APPDATA%\xray\config.json`
- Logs: `%LOCALAPPDATA%\corvex\corvex.log` — append-only, rotated to `corvex.log.1` past 5 MB (0600 is unix-only)
- Xray logs: `%LOCALAPPDATA%\xray\{access,error}.log` by default; configurable via corvex.json `log.xray.*`
